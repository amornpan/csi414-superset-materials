2. เลือก Database `examples` และ Schema `public`
3. พิมพ์คำสั่งนี้ แล้วกด **Run**

```sql
SELECT DATE_TRUNC('month', "Travel Date") AS "เดือน",
       "Travel Class"                      AS "ชั้นโดยสาร",
       AVG("Cost")                         AS "ค่าตั๋วเฉลี่ย",

GROUP BY 1, 2
ORDER BY 1
```

## ตอนที่ 4 — สำรวจข้อมูลขั้นที่ 4: ยืนยันสิ่งที่ตาเห็นด้วยตัวเลข แล้วทำให้เป็นชุดข้อมูลที่พร้อมใช้ (30 นาที)

ใน SQL Lab เลือกฐาน **`examples`** (SQLite) ตาราง `flights`

### 4.1 สามคำสั่งที่ตรวจสอบสามสัปดาห์ที่ผ่านมา (15 นาที)

```sql
-- (1) นับค่าหายทุกคอลัมน์ในคำสั่งเดียว — ต้องได้ 1195 / 1354 / 37299 เท่ากับที่นับด้วยกราฟสัปดาห์ 5
SELECT COUNT(*) AS rows_all,
       SUM(CASE WHEN DEPARTURE_DELAY IS NULL THEN 1 ELSE 0 END) AS null_dep,
       SUM(CASE WHEN ARRIVAL_DELAY   IS NULL THEN 1 ELSE 0 END) AS null_arr,
       SUM(CASE WHEN AIR_SYSTEM_DELAY IS NULL THEN 1 ELSE 0 END) AS null_reason
FROM flights;

-- (2) มีแถวซ้ำไหม — ถ้าสองค่าเท่ากัน แปลว่าไม่มี
SELECT COUNT(*) AS rows_all,
       COUNT(DISTINCT ds || AIRLINE || FLIGHT_NUMBER || ORIGIN_AIRPORT) AS rows_unique
FROM flights;

-- (3) ค่าสัมพันธ์ Pearson r ระหว่าง delay ขาออกกับขาเข้า (SQLite ไม่มี corr() จึงคำนวณจากสูตร)
SELECT (n*sxy - sx*sy) / sqrt((n*sxx - sx*sx) * (n*syy - sy*sy)) AS r
FROM (SELECT COUNT(*) AS n, SUM(DEPARTURE_DELAY*ARRIVAL_DELAY) AS sxy,
             SUM(DEPARTURE_DELAY) AS sx, SUM(ARRIVAL_DELAY) AS sy,
             SUM(DEPARTURE_DELAY*DEPARTURE_DELAY) AS sxx, SUM(ARRIVAL_DELAY*ARRIVAL_DELAY) AS syy
      FROM flights WHERE DEPARTURE_DELAY IS NOT NULL AND ARRIVAL_DELAY IS NOT NULL);
```

| (2) | | |

### 4.2 การตัดสินใจ 3 สัปดาห์ กลายเป็น Dataset เสมือน (15 นาที)

บันทึก SQL นี้เป็น **Dataset เสมือน** ชื่อ `flights_clean_<รหัสนักศึกษา>`

```sql
SELECT rowid AS id, *,
       SCHEDULED_DEPARTURE / 100 AS dep_hour,
       CASE WHEN ARRIVAL_DELAY   >= 15  THEN 1 ELSE 0 END AS is_delayed,
       CASE WHEN DEPARTURE_DELAY > 180  THEN 1 ELSE 0 END AS is_outlier
FROM flights
WHERE CANCELLED = 0 AND DIVERTED = 0
```

- `WHERE CANCELLED = 0 AND DIVERTED = 0` = การตัดสินใจสัปดาห์ 5 (ต้องเหลือ **53,751** แถว)
- `is_outlier` = การตัดสินใจสัปดาห์ 7 (557 แถวที่ flag)
- `is_delayed` = นิยาม "ล่าช้า" ที่ทั้งทีมจะใช้เหมือนกัน (ตรงกับเกณฑ์ ≥ 15 นาทีที่ข้อมูลใช้บันทึกสาเหตุอยู่แล้ว)
- `id` = รหัสแถว ใช้สัปดาห์หน้าตอนพล็อตจุดต่อแถว

จากนั้นเปิด Dataset นี้ → **Metrics** → เพิ่ม metric กลางชื่อ `on_time_rate` = `AVG(1 - is_delayed)` แล้วสร้าง Table `on_time_rate` ตาม `AIRLINE` เรียงมาก→น้อย (VX ควรนำที่ราว 86% และ MQ รั้งท้ายราว 47%)

> สัปดาห์ 5–7 คุณ "ตัดสินใจ" ใน Decision log แต่แดชบอร์ดยังใช้ข้อมูลดิบอยู่ วันนี้การตัดสินใจกลายเป็นโค้ดที่รันซ้ำได้
> ตั้งแต่สัปดาห์หน้า **ทุกกราฟในแท็บสำรวจข้อมูลต้องใช้ `flights_clean` เท่านั้น**

## บันทึกสัปดาห์นี้ (ต้องเขียน)

เปิดกล่อง Markdown บนแดชบอร์ดของคุณ แล้วเขียนต่อท้ายของเดิม

```markdown
## บันทึกสัปดาห์ที่ 8

(เขียนที่นี่ อย่างน้อย 60 ตัวอักษร)
```

**ห้ามลบบันทึกของสัปดาห์ก่อน** ตัวตรวจตรวจสะสม ลบแล้วตกย้อนหลัง
เหมือนลบกราฟเก่าทิ้ง

สิ่งที่ควรเขียนถึง

- Dataset เสมือนต่างจากการเขียนสูตรซ้ำในแต่ละกราฟอย่างไร และข้อดีคืออะไร
- คุณย้ายสูตรอะไรไปเป็น metric กลาง และถ้าวันหนึ่งนิยามนั้นต้องเปลี่ยน คุณต้องแก้กี่ที่
- SQL Lab กับ Explore เหมาะกับงานคนละแบบอย่างไร ยกตัวอย่างงานที่ต้องใช้แต่ละอย่าง
- ผลจาก SQL ตรงกับที่นับด้วยกราฟไหม ถ้าไม่ตรงต่างกันตรงไหน และ `flights_clean` ของคุณเหลือกี่แถว เพราะอะไร

> เขียนสิ่งที่ **เห็น** ไม่ใช่สิ่งที่ **ทำ**
> "ทำกราฟเส้นเสร็จแล้ว" ไม่ได้บอกอะไรกับคนอ่าน
> "เปลี่ยนจาก SUM เป็น AVG แล้วรูปเปลี่ยนไปคนละเรื่อง" บอก

**ตัวอย่างแนวการเขียน** — เขียนของคุณเองจากตัวเลข/สิ่งที่เห็นจริงบนแดชบอร์ด อย่าลอกทั้งดุ้น (ระบบลายนิ้วมือกันลอกจับความซ้ำได้ และคะแนนบันทึกให้กับการเขียนสิ่งที่คุณเห็นเอง)

> Dataset เสมือนเก็บสูตรไว้ที่เดียว ต่างจากพิมพ์ AVG(Cost) ซ้ำในทุกกราฟ ข้อดีคือแก้นิยามที่เดียวมีผลทุกกราฟพร้อมกัน ย้ายสูตรค่าตั๋วเฉลี่ยไปเป็น metric กลางของ Dataset วันหนึ่งถ้านิยามต้องเปลี่ยนก็แก้ที่เดียวแทนที่จะไล่แก้ 5 กราฟและเสี่ยงลืมไปหนึ่งรูป SQL Lab เหมาะตอนต้อง join หลายตารางเข้าด้วยกัน ส่วน Explore เหมาะงานกราฟทั่วไปที่ไม่ต้องเขียน SQL
